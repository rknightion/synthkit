## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
GPU telemetry is the centre of every AI Factory journey: utilisation, memory, temperature, power, clocks, throttle reasons, ECC, row remapping, Xid and NVLink errors, and DCGM health. dcgm-exporter runs per GPU node and is scraped either by a host Alloy or through the k8s-monitoring DCGM integration. Cardinality facts established while sizing real estates: the stock default-counters.csv at dcgm-exporter 4.6.x to 4.8.x has 26 rows, one of which (DCGM_FI_DRIVER_VERSION) is a label-type row, giving about 25 series per GPU; adding the counters that GPU fault alerting needs (ECC, throttle violation, clock events, Xid, health) takes it to about 49. DCGM_EXP_GPU_HEALTH_STATUS emits one series per health watch (about 11 per GPU); DCGM_EXP_CLOCK_EVENTS_COUNT emits one series per GPU and reason; DCGM_EXP_P2P_STATUS is N x (N-1) per node and belongs off by default. Kubernetes mode adds pod, namespace and container labels only while a pod holds the GPU, which is the standard job-to-GPU join when no source emits exemplars. NVL72 nodes add NVSwitch and Grace CPU entities.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 A dcgm construct emits the stock counter set by default, with blueprint-selectable counter profiles (stock, fault-detection additions, DCP profiling fields) and P2P status off by default; series per GPU in just dump matches the documented count for each profile
- [ ] #2 Host mode and Kubernetes mode are both supported; in Kubernetes mode pod, namespace and container labels exist only while a workload pod is bound to the GPU and join to kube-state-metrics pod series and to the GPU fixture
- [ ] #3 NVL72 nodes emit the NVSwitch and Grace CPU entity families the way dcgm-exporter does on that platform, or the gap is PENDING in cantfind.md; MIG is supported or explicitly deferred
- [ ] #4 Failure modes cover Xid bursts, ECC error growth with row remapping, sustained thermal or power throttling, a GPU falling off the bus (its series disappear), DCGM health failure and NVLink errors, and are listed in docs/incidents.md
- [ ] #5 Values are physically consistent: utilisation follows scheduler allocation when a scheduler construct is present, power and temperature stay inside the GPU model's envelope, counters are cumulative
- [ ] #6 signals/dcgm.md documents every field against a pinned dcgm-exporter tag and counters file
- [ ] #7 Every metric, label, attribute and log field is sourced from vendor documentation or a capture at a pinned version and recorded with provenance in the named signals/ area file; anything unconfirmed is a PENDING in cantfind.md, never an invented name
- [ ] #8 Rates, counts and cardinality in any shipped blueprint are plausible for a real deployment, with the real-world basis stated in a comment; nothing is raised to force emission
