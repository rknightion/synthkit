## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Platform automation (node provisioning, firmware rollout, drain and return to service, storage provisioning, self-service portals) is where AI Factory designs use traces: workflow and task duration, retries, failures, approvals, target system, API status and latency, with trace-derived metrics for long-term reporting. Spans carry operational metadata only, never payloads, secrets or command output. Platform traces and user workload traces are routed to different stacks by the collector, so a classifying resource attribute is needed to exercise that routing. The app workload's workflow node type may already cover most of this.
<!-- SECTION:DESCRIPTION:END -->

## Acceptance Criteria
<!-- AC:BEGIN -->
- [ ] #1 If the existing app workload DSL can express these workflows, the delivery is blueprint content only; otherwise the smallest DSL extension is made
- [ ] #2 Workflows emit spans with retries, failures and approval steps, and the matching span-derived metrics, using only attributes the app DSL and semantic conventions allow
- [ ] #3 Platform and workload traces are distinguishable by a documented resource attribute so collector routing pipelines can be tested against them
- [ ] #4 Rates, counts and cardinality in any shipped blueprint are plausible for a real deployment, with the real-world basis stated in a comment; nothing is raised to force emission
